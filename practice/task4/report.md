# Аномалии изоляции в SQL

---

## 1. Подготовка тестовой среды
```sql
CREATE TABLE score (
    id INT PRIMARY KEY,
    name TEXT,
    balance INT
);

INSERT INTO score (id, name, balance) VALUES 
(1, 'Ivan', 1000), 
(2, 'Petr', 2000);
```

---

## 2. Воспроизведение аномалий

### Аномалия №1: Dirty Read (Грязное чтение)
**Описание:** Ситуация, при которой транзакция читает данные, измененные другой транзакцией, которая еще не была зафиксирована (`COMMIT`).

**Шаги воспроизведения:**
Для воспроизведения данной аномалии использовалась СУБД **MySQL**, так как PostgreSQL защищен от грязного чтения на уровне архитектуры. В MySQL был установлен минимальный уровень изоляции — `READ UNCOMMITTED`.

1. **Транзакция А (Т1):** Устанавливает уровень `READ UNCOMMITTED` и читает баланс Ивана. Результат: **1000**.
2. **Транзакция Б (Т2):** Начинает транзакцию и выполняет команду `UPDATE accounts SET balance = 500 WHERE id = 1;`. Команда выполнена успешно, но **COMMIT еще не сделан**.
3. **Транзакция А (Т1):** Снова выполняет `SELECT balance FROM accounts WHERE id = 1;`.

**Результат:** 
Транзакция А увидела измененное значение **500**, хотя Транзакция Б еще может отменить свои изменения (`ROLLBACK`). 

---

### Аномалия №2: Lost Update (Потерянное обновление)
**Описание:** Две транзакции одновременно читают данные, после чего обе вносят изменения. В результате изменения первой транзакции перетираются второй.

**Шаги воспроизведения (Уровень: Read Committed):**
1. **Т1:** Читает баланс Ивана (1000).
2. **Т2:** Читает баланс Ивана (1000).
3. **Т1:** Прибавляет 100 и записывает: `UPDATE accounts SET balance = 1100 WHERE id = 1; COMMIT;`
4. **Т2:** Прибавляет 200 к своему (старому) значению и записывает: `UPDATE accounts SET balance = 1200 WHERE id = 1; COMMIT;`

**Результат:** 
Финальный баланс — 1200 руб. Обновление из Транзакции А (+100 руб.) было полностью потеряно.

---

### Аномалия №3: Non-repeatable Read (Неповторяющееся чтение)
**Описание:** Повторное чтение одних и тех же данных внутри одной транзакции выдает разные результаты из-за изменений, зафиксированных другой транзакцией.

**Шаги воспроизведения (Уровень: Read Committed):**
1. **Т1:** `BEGIN; SELECT balance FROM accounts WHERE id = 1;` — Видит 1000.
2. **Т2:** `UPDATE accounts SET balance = 0 WHERE id = 1; COMMIT;`
3. **Т1:** Повторяет запрос: `SELECT balance FROM accounts WHERE id = 1;` — Видит 0.

**Результат:** 
Транзакция А получила разные данные внутри одной логической единицы работы.

---

### Аномалия №4: Phantom Read (Фантомное чтение)
**Описание:** Повторное чтение с наложением фильтра выдает разное количество строк из-за добавления новых записей другой транзакцией.

**Шаги воспроизведения (Уровень: Read Committed):**
1. **Т1:** `BEGIN; SELECT COUNT(*) FROM accounts;` — Результат: 2.
2. **Т2:** `INSERT INTO accounts VALUES (3, 'Oleg', 3000); COMMIT;`
3. **Т1:** `SELECT COUNT(*) FROM accounts;` — Результат: 3.

**Результат:** 
В Транзакции А появилась «фантомная» строка, которой не было при первом чтении.

---

## 3. Как избежать аномалий

Для устранения описанных проблем в СУБД используются более высокие уровни изоляции или специальные механизмы блокировок:

1. **Избежание Dirty Read:** Использовать уровень изоляции `READ COMMITTED` и выше.
2. **Избежание Lost Update:** 
   - Использование атомарных операций: `UPDATE accounts SET balance = balance + 100`.
   - Повышение уровня изоляции до `REPEATABLE READ` (в этом случае PostgreSQL выдаст ошибку сериализации, если строка была изменена другой транзакцией).
3. **Избежание Non-repeatable Read:** Установка уровня изоляции `REPEATABLE READ`. Транзакция будет видеть «снимок» данных на момент своего начала.
4. **Избежание Phantom Read:** Установка уровня изоляции `SERIALIZABLE`. Это самый строгий уровень, который гарантирует, что результат параллельного выполнения транзакций будет таким же, как если бы они выполнялись строго по очереди.
